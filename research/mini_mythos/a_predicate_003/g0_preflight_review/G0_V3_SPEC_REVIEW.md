## 3. F-18：放行证据

* **现状（`g0_run.py` 的 `Guard.g_write`）**：对门的写 `b"R"`，先 `release_pre.append(mono)`，再调用真实 `os.write`。列表只记录了「尝试之前的时间」，写入若抛 `BrokenPipeError`，列表里仍有一项。V2 的 C07 与 C03 的 `release_byte_written` 都把这一项当作「放行字节已写入」。
* **三个事实**：尝试 = `guard.release_writes[k].mono_before`；成功写入 = 该项 `result='ok'`、`returned==1`、`mono_after`；通过门控 = 子进程自己的 `FIRST_ACTION`（它在读到 `R`、再读到 `SPEC` 之后才发出，而 `SPEC` 在写入返回之后才发送，所以 `FIRST_ACTION` 必然晚于 `mono_after`；早于则是门被绕过 ⇒ C07-F4）。
* **V3 的处理**：C07 见 §1；C03 的 `release_attempt` / `release_write_ok` / `gate_passed` 为独立定义；`release_writes` 是必需证据（C16）；写入失败是被记录的事实，而不是缺失。
* **最小案例**（§5）：R1 成功；R2 EPIPE；R3 成功但无 FIRST_ACTION；R4a/b/c 有 FIRST_ACTION 但登记不完整的三种成因；R5a–e 登记表 / 账本 / 写入器序号的五种不一致；R6 写入失败而子进程仍通过；R7 FIRST_ACTION 早于写入完成；R8a/b 无尝试记录；R9 尝试早于 RELEASED 记录；R10 两次写入。

## 4. C16：相对 V2 的语义变化（正确标记）

* **要求增加：** `evidence_schema`、`consumed_dir`、`guard.release_writes`（取代 `guard.release_byte_pre_write_monos`）；每个字段的**类型**；类型错误按缺失处理，`bool` 不被当作 `int` / `number`。
* **要求替换：** V2 的「内存记录数」⇒ `reg_memory_records`（账本）+ `reg_writer_seq`；记录数由账本导出，不再单独记录。
* **PASS→BLOCKED 的方向：** 只符合 V2 的证据（缺 `reg_memory_records`、`reg_writer_seq`、`evidence_schema`、`consumed_dir`、`release_writes`）在 V3 下 C16 失败 ⇒ **BLOCKED**（CE-E1）；反方向（V3 证据不符合 V2）不适用，因为 V2 从未被执行。
* **校验时机：** 判定函数一次、先于所有检查、在 `json.loads(json.dumps(evidence))` 的类型上；`g0_run` 的自检仅作诊断。
* **C16 不判什么：** 登记见证之间的一致性（那是 C03）；记录内部字段（`reg_memory_records` 元素只验证容器 `seq:int, kind:string`，其余字段由 C03-F1(d) 判定，CE-E5）。
* **已知限度：** 保真检查只比较 `(seq, kind, node_id)` 三元组，记录其他字段被改动不会被发现（写入 `policy_notes.fidelity_scope`）。
