## 1. 目标与分工

**目标**:以 Parcae-140M 为底座,参考 OpenMythos 的机制设计,做出“Parcae + 我们的机制”,并用实验证明它比原生 Parcae 更好:同等计算下质量更高,或相近质量下计算更少。

| 名称 | 角色 |
|---|---|
| Parcae | 底座:网络结构、预训练权重、原生对照 |
| OpenMythos | 机制清单与参考实现;是推测性重建,不是 Claude 的真实架构 |
| Mythos | 我们验证有效后的模型,属于 **Parcae 的派生模型**(Parcae 权重 + 我们的机制),不是独立权重。不宣称复刻 Claude Mythos |

| 参与者 | 职责 |
|---|---|
| 项目负责人(用户) | 决定方向、预算、是否进入下一阶段 |
| Claude Project(策略助手) | 设计实验、审方案、解读结果、控制成本 |
| Claude Code(在 Codespace 或 GPU 机器上运行) | 写代码、执行、提交证据和简短 checkpoint |

## 2. 名词小词典

- **Token**:模型读文字的最小单位,像把句子切成小积木。
- **BOS**(Beginning Of Sequence,开头记号):一个可以放在文字最前面的特殊记号,意思是“新的一段从这里开始”。**Parcae 训练时没有用它**,所以我们评测时也不加;加了反而会让模型变差(阶段 0 实测)。
- **NLL / 困惑度**:衡量模型猜下一个词的本事。数字越小越好。困惑度 29 大约表示模型平均在 29 个候选里犹豫。
- **递归轮数(深度)**:Parcae 会用同一套网络反复思考几遍。训练时平均 8 轮;我们测过 16 轮、32 轮。
- **适配器 / LoRA**:在冻结的大模型旁边加一个很小的可训练零件,用来学新本事,不改原权重。
- **领域适配**:模型在某类文章上多练几下,就会更擅长那类文章,但不代表它整体变聪明了。这是我们之前误判“机制有效”的主要原因。
- **开发集 / 新数据集**:开发集可以反复用来调试;新数据集是从没用过的文章,用来检验是否真的变好。

## 3. 当前可信事实

1. 官方加载器能逐字节恢复 Parcae-140M 的全部 63 项状态(含 RoPE 位置编码缓冲区)。
2. CPU 前向计算确定、可复现;新进程重载结果一致。
3. 阶段 0(无 BOS,正确输入):在 100 篇 WikiText 和 100 篇 C4 新文本上,16、32 轮比 8 轮显著更好,但只好约 0.2–0.3% 困惑度,计算是 1.69 倍和 3.05 倍;同分布的 FineWeb 上不显著。旧的“提升 3–4%”只在旧的 32 段样本上成立。8 轮 CPU 速度约 198 tokens/s(2 线程)。
3b. 自适应深度没有空间:连用了答案的理想路由也不比固定 8 轮更值。这条线关闭。
4. 自适应深度控制器(TV≤0.01)质量不变,但比固定 32 轮更慢。这条路线目前是负结果。
5. 已训练的适配器(按深度 LoRA、循环编号、MoDA)在开发集上有收益;但 MoDA 换到新领域(AG News)后比原生模型差 0.19–0.26 nats。
6. 官方 CORE 评测(受限模式,每任务 12 例)两个种子得分 10.59、11.46,完整 CORE 未跑。

**基线已建立**(阶段 0):官方加载器、无 BOS、8 轮、CPU FP32;主指标 NLL:wikitext 3.2267、c4 3.3169、fineweb 2.8734。

**阶段 2 已建立**(GPU,RTX 4090):GPU FP32 与 CPU 逐窗口差 ≤1e-6;bf16 评估偏差约 0.001,评估一律用 FP32。无机制微调(LoRA r8、全参数)2000 万 token 后各领域开发集变化都在 ±0.003 以内;训练噪声下限 ≤0.002;可检出的效应约 0.002–0.003 nats。每 1000 万训练 token 约 $0.05。GPU 续训统计一致(非逐位)。详见 `stage2/CHECKPOINT.md`。

**阶段 3a(MoDA-P)FAIL**:测试集上相对同参数 LoRA,仅书籍改善 0.0013 nats,其余领域无效果,未达 0.003 门槛;门控几乎没打开(深度输出约占注意力输出的 1.5%)。另发现:上游式打包只用上 48% 语料(每次约 2400 万 token)。详见 `stage3/CHECKPOINT.md`。

**尚未建立**:合理的生成质量评估(需用无 BOS 重跑生成);任何机制在新数据上的收益。

## 4. 已知问题与教训

1. **BOS 判断曾经出错**:审计时误以为训练加了 BOS,阶段 0 实测和训练管线源码都表明训练没加。正确做法是不加 BOS。教训:涉及训练约定的判断,要查实际训练管线,不能看默认参数。
2. **生成质量判据不合理**:贪心解码 64 个 token 就判重复失败,对小模型几乎必败。要换成采样解码,或直接用困惑度和 CORE。
3. **采样守卫写错**:FP32 概率和的容差设成 1e-6,正常误差就会触发。要修。
4. **训练数据太小太单一**:2000 token、单一领域,收益主要是领域适配,不是机制。
5. **缺关键对照**:必须有“同预算、不加机制”的微调对照,并以新领域数据为主指标。
6. **流程过重**:很多尝试死于路径、导入、证据体积等运维问题。

## 5. 工作规则(精简版)

保留:
- 每个实验先写**一页**方案:目的、数据、对照、主指标、通过标准、预算上限。
- 方案冻结后再跑,不看结果改标准。
- 状态如实写:PASS / FAIL / BLOCKED / NOT TESTED。
- 每次只加一个机制;组合要等单项在新数据上通过。
- 每个机制都要有:原生对照 + 同预算无机制对照 + 新领域测试集。
- **同预算**写死为:可训练参数量相同、训练 token 数相同、学习率等超参搜索次数相同。
- **异领域新集要查污染**:Parcae 预训练语料是网页类文本(FineWeb-Edu),WikiText、C4、AG News 等公开数据可能部分被见过。阶段 1 至少抽样做一次 n-gram 重叠检查。

去掉:
- 对数万个历史文件逐个哈希保护。
- 每个实验重写启动器和守卫。
- “预算超时即判 BLOCKED 不许续跑”。改为:允许续跑,但必须如实记录。

证据只保留到“别人能复核”为止:代码版本、配置、随机种子、汇总结果、关键原始输出。

## 7. 资源与预算(粗略估计,需实测确认)

- Parcae-140M 在 8 轮下前向约 0.35 GFLOPs/token,训练约 1 GFLOP/token。**这是源码推算值,需实测**:循环核心每轮都要重复计算,实际可能更高。阶段 0 会记录 CPU 实测 tokens/s,据此校准 GPU 预算。
- 1000 万 token 的适配训练约 1e16 FLOPs。单张 A100 或 4090 级显卡大约**几分钟到十几分钟**;1 亿 token 约 1 小时量级。32 轮会贵约 4 倍。
- 按租用价格每小时约 0.5–2 美元估算,单个机制实验大约几美元级。**主要成本在调试时间,不在算力。**
- 省钱原则:CPU 做数据准备、正确性测试和小评估;GPU 只跑冻结后的正式训练;每次租用前确认代码已在 CPU 上用小数据跑通。
