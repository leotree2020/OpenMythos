# Stage 0 复核(Claude Code 云端会话,2026-11-08)

复核对象:`CHECKPOINT.md` 与 `results/`(提交 `16375395`)。执行与数据本身没有问题;问题出在方案里的 BOS 前提。

## 1. 更正:Parcae 预训练没有加 BOS,我之前的判断错了

审计报告问题 1 与宪章 v2.0 第 3.7 条都假设“训练加了 BOS”,依据是 `recpre/data_loading_utils.py` 里 `add_bos=True` 这个默认值。这个判断错了。实际训练管线如下(固定上游 `69284c13`):

- `launch_configs/parcae-small-140m.yaml`:`type: pqds-pure`,`pack_sequences: True`。
- `recpre/huggingface_dataset.py` 的 `ParquetStreamPure._read_buffer`:原始文本用 `tokenizer.encode(text, return_tensors=False)` 编码,没有传 `bos`/`eos`,所以既不加 BOS 也不加 EOS。产出的是 torch 张量。
- `recpre/data_loading_utils.py` 的 `BestFitPackingCollator._tokenize_row`:输入已经是张量时原样返回,不再加任何特殊 token。`add_bos/add_eos` 只作用于字典格式的行(`settings.py` 注释写着“HFDS only”)。
- 打包方式是 best-fit,整篇文档首尾相接,不加分隔符。所以训练时大多数行从“某篇文档的第一个 token”开始,前面没有 BOS。

结论:**不加 BOS、从文档开头取窗口,才与训练一致。** 实测也支持这一点:加 BOS 后三个新领域的主指标都变差 0.07–0.10 nats,前 64 个 token 变差 0.38–0.49 nats;生成也严重退化(例如 “is is is is…”)。官方 CORE 评测(`receval/tasks/core_eval.py`)会强制加 BOS,与训练不一致。这可能压低了官方 CORE 分数,但不影响我们的结论。

旁证:`wikitext_old32` 在无 BOS、8 轮下的 NLL 是 3.3775,旧实验是 3.3786。打分范围差 1 个 token、种子不同的情况下,两者相差 0.001,说明代码复现了旧结果。

## 2. 按正确输入(无 BOS)重读结果

以下数字都是本次运行已经算出、已在 `summary.md` 中的数值,没有新增计算。冻结的三选一判断写的是“BOS 开启”,因为方案以为 BOS 是正确输入;现在输入约定已更正,这里按无 BOS 重新陈述。这属于看到结果后的更正,如实标明。

| 领域 | 无 BOS d8 | d16−d8 [95% CI] | d32−d8 [95% CI] | PPL 变化(d16 / d32) |
|---|---:|---|---|---|
| wikitext | 3.2267 | −0.0022 [−0.0035, −0.0009] | −0.0022 [−0.0037, −0.0007] | −0.22% / −0.22% |
| c4 | 3.3169 | −0.0027 [−0.0044, −0.0010] | −0.0028 [−0.0048, −0.0007] | −0.27% / −0.28% |
| fineweb(参照) | 2.8734 | −0.0008 [−0.0023, +0.0006] | −0.0007 [−0.0024, +0.0009] | −0.08% / −0.07% |
| wikitext_old32 | 3.3775 | −0.0315 [−0.0498, −0.0182] | −0.0369 [−0.0613, −0.0201] | −3.10% / −3.62% |

- **无 BOS 下的三选一:16 轮和 32 轮在两个验收领域都显著优于 8 轮,但幅度只有约 0.2–0.3% 困惑度,代价是 1.69 倍和 3.05 倍计算。** 同分布的 fineweb 上没有显著收益。
- 旧实验那 32 段上的约 3% 收益确实可以复现,但它不能代表普通文本:同类的 100 篇新 WikiText 文章上只有 0.2%。旧的“16/32 轮提升 3–4%”这个说法应改为“只在特定样本上成立”。
- 实际意义:对这个 140M 模型,推理时加深递归几乎不划算。后续机制实验的原生对照用 8 轮。

## 3. 自适应深度:没有空间,关闭这条线

方案第 3 条规则写的是“事后最优上界的成本低于固定 32 轮的 75%”,字面上满足(34–36%)。但这条规则设计得不好:固定 8 轮的成本只有固定 32 轮的 29%,而质量与事后最优上界相差不到 0.004 nats。也就是说,连“用了答案的理想路由”都不比“永远用 8 轮”更有价值。结论:自适应深度这条线关闭。

## 4. 其他

- **生成**:本次生成按方案加了 BOS,结果严重退化,不能代表模型。`generate.py` 已改为默认不加 BOS(`--bos` 只作对照)。建议重跑一次生成,约 15–30 分钟。
- **速度**:256 token 前向,8 轮约 198 tokens/s(2 线程,AMD EPYC 7763)。16 轮 1.69 倍,32 轮 3.05 倍。
- **执行记录**:中途有两个进程重叠约 1 分钟,产生 3 行重复,数值逐位相同,汇总时已忽略;有一段日志被覆盖。这些不影响结果。

## 5. 基线定义(供后续阶段使用)

Parcae-140M,官方加载器;输入不加 BOS,从文档开头取窗口;递归 8 轮;CPU FP32。主指标为 t[65..255] 的 NLL。各领域基线 NLL:wikitext 3.2267,c4 3.3169,fineweb 2.8734。
