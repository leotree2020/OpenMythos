**核心事实（来自 G1/G2 证据）：**
1. R3 条件 (1)「直接子进程尚未被 `waitpid` 回收」是**账目事实**：子进程已退出但未回收时它持续为真。
2. R3 条件 (2)「`killpg(pgid, 0)` 仍成功」对只含僵尸的进程组仍成功（回收后才 ESRCH）。
3. R3 文字没有规定 A 的求值与 `waitpid(WNOHANG)` 的先后；三种读法（不回收 / 先求值再回收 / 先回收再求值）里，只有「先回收再求值」在全部用例都与意图一致。
4. 因此按字面，A 在「已退出未回收」时为真，宽限用尽会**错误升级 SIGKILL**。

## 2. 修订必须满足的要求（候选方案的共同验收尺度）

| RA-1 | **语义**：A 为假 ⇔ 所有目标进程都已退出（僵尸 = 已退出）；A 为真 ⇔ 存在仍在运行（或无法证明已退出）的目标 | R3 §11.1(d) 的原意 |
| RA-2 | 已退出但未回收的**直接子进程**不得使 A 为真 | G1-02、G2 门禁 |

| RA-4 | 活跃后代与僵尸后代并存时：有活跃目标则 A 为真；僵尸目标不使 A 为真，但在 `confirmed` 之前必须被回收（若属于我们的职责） | G5 的规划 |
| RA-5 | **被重新挂靠的后代**（`PR_SET_CHILD_SUBREAPER`）要被看见：活的使 A 为真，僵尸的要回收 | G5 |
| RA-6 | SIGTERM 到宽限期截止的竞态：在截止点前后退出的进程不得引起错误的 SIGKILL；发 SIGKILL 前必须**再次**确认仍有活跃目标 | G2-02 |

| RA-8 | **不得意外回收其他进程**（监督器的辅助子进程、其他实验或系统进程）；回收只能针对已登记并验证的 pid | 安全；R3 T5 现有的 `waitpid(-1, WNOHANG)` 违反此条 |

## 3. 两个候选方案的共同部分

下面几项对方案 A、方案 B **相同**，因此不是二者的差别：

- **目标集合与身份锚点：** 每个阶段以 `start_new_session=True` 启动，其会话号 `sid` = 进程组号 = 直接子进程 pid。目标 = 登记的直接子进程 + 会话号等于该 `sid` 的全部进程 + 经验证的重新挂靠后代。**用 `/proc/<pid>/stat` 的会话号匹配，不用 `killpg(pgid, 0)` 的返回值**（后者降为只记录的「参考观察」）。
- **指纹：** 在 spawn 时记录 `(pid, starttime, sid, pgrp)`（`starttime` 是 `/proc/<pid>/stat` 第 22 项，开机后的时钟节拍，同一次开机内与 pid 一起唯一标识一个进程）；之后任何信号或回收之前先核对指纹。目的：RA-7、RA-8。
- **存活判定：** 目标 `/proc` 状态是 `Z`（僵尸）或 `X`（已死）→ 不计入存活；其余（`R`、`S`、`D`、`T` 等）→ 存活。
- **子收割者前提：** 监督器在 S0 预检里设置 `PR_SET_CHILD_SUBREAPER`；设置失败 → S0 `BLOCKED`（`PREFLIGHT_FAILED`），因为否则重新挂靠的后代会被 init 收养而不可见（RA-5、RA-9）。
- **T5 的回收规则：** 删去 `waitpid(-1, WNOHANG)`；只对**已登记且指纹验证通过**的 pid 调用 `waitpid(pid, WNOHANG)`。
- **SIGKILL 前复核：** 发 SIGKILL 之前，立即重新计算一次 A（同一方案的 A），为假则**取消升级**（RA-6）。信号只发给指纹验证通过的存活目标；组信号仅在组内仍有存活的、指纹匹配的成员时才使用，否则逐 pid 发送（RA-7）。
- **`/proc` 不可用或扫描出错 → A 无法求值 → BLOCKED `TERMINATION_UNCONFIRMED`**，不得当作 A 为假（RA-9）。

> 关于 PID/PGID 复用的内核事实（需受控测试验证，本草稿未验证）：只要还有任何进程以某编号作为进程组号或会话号，该编号就不会被分配给新进程；叶进程被回收后，若组内仍有成员，编号仍被占用；组清空且叶进程被回收后编号才可能复用。所以「回收之后再对旧 pgid 发信号」才是危险点，指纹核对要覆盖它。

## 4. 方案 A：先回收后求值（reap-first）

**机制（草案条款，不适用于冻结版）：** 每个轮询周期按序：
1. 对每个已登记的直接子进程 `waitpid(pid, WNOHANG)`（具体 pid，**不用 `-1`**）。返回该 pid → **立即**把退出状态写入内存记录 `exit_record`（退出码或信号、`CLOCK_BOOTTIME` 时刻）并标记已回收；返回 0 → 尚未退出。
2. 扫描 `/proc`（会话号匹配，见第 3 节）；`ppid` 为监督器、会话号相符、指纹验证通过的重新挂靠**僵尸**后代 → `waitpid(该 pid, WNOHANG)` 回收，状态记入 `exit_record`。
3. **A 为真 ⇔** 步骤 1 中有直接子进程尚未退出，**或**步骤 2 中存在状态不是 `Z`/`X` 的目标。条件 (1) 改述为「直接子进程尚未退出」。

**优点：** 与 R3 现有的 `waitpid(WNOHANG)` 轮询（§11.1(c)5）一致，Python 的 `Popen.poll()` 本来就是这种行为；回收与观察一步完成；僵尸不会累积。
**缺点 / 风险：** 观察有副作用（回收会消耗状态），所以必须在回收瞬间保存退出状态；回收后 pid 被释放，复用风险窗口提前；与 `subprocess.Popen` 混用时必须统一由同一处回收，否则 `Popen` 会误判；轮询里的回收一旦放宽到 `-1` 就会误回收其他进程（必须严格按 pid）。

## 5. 方案 B：非消耗式观察（observe-then-decide）

**机制（草案条款，不适用于冻结版）：** 每个轮询周期**只观察，不回收**：
1. 对每个已登记的直接子进程 `waitid(P_PID, pid, WEXITED|WNOHANG|WNOWAIT)`：无状态变化 = 仍在运行；有结果 = 已退出（状态保留在内核，**未被消耗**）。
2. 扫描 `/proc`（会话号匹配）；僵尸成员只观察，不回收。
3. **A 为真 ⇔** 步骤 1 中有直接子进程无状态变化，**或**步骤 2 中存在状态不是 `Z`/`X` 的目标。
4. 回收**一律推迟到 T5**，只按具体 pid、指纹验证通过后回收，此时退出状态仍在内核里（也可由 `waitid` 的结果读取）。

**优点：** 观察与回收分离，轮询不改变系统状态，竞态分析更简单；退出状态不依赖监督器内存；对「求值顺序」不再敏感。
**缺点 / 风险：** 僵尸在整个宽限期内保留，直到 T5；需要额外的 T5 回收步骤正确执行；`waitid(P_ALL, …)` 会窥探任何子进程的状态变化，**必须只用 `P_PID`**；`WNOWAIT` 对已停止 / 恢复状态的行为不在本草稿范围；实现者容易漏掉 T5 而留下僵尸。

## 6. 两方案与基线的逐项比较（草案判断，须由受控测试验证）

基线 = 冻结 R3 的字面 A（G1/G2 已证明在若干读法下失败）。「预期」是按机制推断的，**不是测试结果**。

| 考虑项 | 基线（R3 字面） | 方案 A | 方案 B |
|---|---|---|---|
| 已退出未回收的直接子进程 | A 为真（错）；NOREAP / EVAL_THEN_REAP 读法错误升级 | 回收后 A 假；退出状态在回收时保存 | `waitid` 看到已退出，A 假；状态留在内核 |
| 进程组只剩僵尸成员 | 条件 (2) 仍成功（错） | `/proc` 状态 `Z` 不计入，A 假 | 同 A |
| 活跃后代与僵尸后代并存 | 条件 (2) 全真，无法区分 | 只要有非 `Z` 目标 A 真；僵尸后代按 pid 回收 | 只要有非 `Z` 目标 A 真；僵尸后代 T5 回收 |
| 被重新挂靠的后代 | 条件 (3) 未规定是否排除僵尸，字面上僵尸后代也是「后代」（有歧义） | 子收割者 + 会话号 + 指纹；活的 A 真，僵尸回收 | 同 A（观察，T5 回收） |
| SIGTERM 到宽限截止竞态 | EVAL_THEN_REAP 读法在宽限点出错 | 先回收后求值，无顺序依赖；SIGKILL 前复核 | 纯观察，无顺序依赖；SIGKILL 前复核 |
| PID / PGID 复用 | 未处理 | 指纹核对；回收后不再对旧 pgid 发信号 | 同 A（回收推迟到 T5，复用窗口更晚开启） |
| 误回收其他进程 | T5 的 `waitpid(-1)` 会误回收监督器的其他子进程（**基线缺陷**） | 只对登记 pid；若退化为 `-1` 同样会误回收（实现风险） | 轮询零回收；T5 只对登记 pid（实现风险较小） |
| 对 `/proc` 的依赖 | 条件 (3) 已依赖 | 依赖 | 依赖 |
| 与现有 R3 文字的改动量 | — | A 的定义、T3、T5 | A 的定义、T3、T5（增加「T3 只观察」） |
| 对 `subprocess.Popen` 的兼容 | — | 与 `Popen.poll()` 同行为，容易对齐 | 需自己调用 `waitid`（`Popen` 不提供），监督器要自管子进程 |

**起草者倾向（非决定、非约束）：**方案 B 把「观察」与「回收」分开，竞态与误回收风险更小，我倾向于 B；但方案 A 与 `Popen.poll()` 和现有 R3 轮询文字更贴近、实现更简单。两者的真实差别应由第 7 节的同一套受控用例裁决，而不是由偏好裁决。
