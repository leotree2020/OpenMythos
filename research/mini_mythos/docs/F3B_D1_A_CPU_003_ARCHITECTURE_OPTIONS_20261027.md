## 1. 问题分解：三个责任问题

监督器要回答的不是「进程什么时候死」，而是：

| 责任 | 问句 | CPU-001 / 002 的事实 |
|---|---|---|
| **归属（Ownership）** | 哪些进程**属于**当前阶段，因此可以被发信号、被回收？ | `_discover()` 的 `sid_hint`、`closed_world_orphan` 依赖未验证的前提；违反前提时 40/40 次误杀或误回收，并可能错误报告 `EXITED`（CPU-002 E1）。正确启动时内核保证阶段会话里只有阶段成员（E1-S1：跨会话 `setpgid` → `EPERM`） |
| **消费（Consumption）** | 谁有权**消费**子进程的退出状态（`wait*` 的消耗式读取）？ | 内核只保存一份状态。CA 先消费 → `Popen.returncode` 静默得 0（15/15；竞态 42/50）。CB 非消耗式观察，但 T5 一消费同样与 Popen 冲突（E2-08a）。Popen 在 `ECHILD` 时设 `returncode = 0` |
| **恢复（Recovery）** | 监督器突然死亡后，谁终止遗留目标、回收僵尸、保全已取得的状态？ | 存活目标继续运行（两臂相同）；CB 未回收状态在新父进程可读，CA 已回收的状态随监督器内存消失；无外层子收割者时由 pid 1 清理僵尸（本环境 1.2–2.2 s，**不可推广**）（E3-02）。冻结 R3 只规定**证据层**的后验模式（11.9 F4，`--postmortem` 只读）；**没有规定进程层**的恢复责任 |

三者互相影响：恢复需要知道「哪些进程属于我」（依赖归属的**持久化登记**）；消费方式决定崩溃时状态是否还在内核里（CB 式）或只在内存里（CA 式）。因此第 4 节给出跨问题的依赖表。

## 2. 归属（E1）候选

目标：**强制验证**的安全前提 + **失败即安全**（无法确认归属 → `UNKNOWN`，不发信号、不回收）。

### 2.1 候选清单

| 编号 | 机制 | 思路 | 来自 |
|---|---|---|---|
| O-0 | 原 `_discover()`（CPU-001 的 CA / CB） | `sid_hint`、`closed_world_orphan` | 已测：前提违反时**失败即不安全** |
| O-1 | 严格归属（CA-S / CB-S） | `sid_hint` 仅当根为独立会话领头；不再使用封闭世界孤儿；`starttime` 早于根的无关子进程忽略，否则 `UNATTRIBUTABLE`；辅助进程后代记为 `aux_family` | 已测（仅 E1）：40/40 零违反；P2 中真后代 → `UNKNOWN`；未在 CPU-001 全矩阵重跑 |
| O-2 | **启动登记表 + S0 强制检查**（设计推断） | 所有子进程只能经单一入口 `spawn_stage()` / `spawn_aux()` 创建，创建瞬间登记 `(pid, starttime, sid, pgrp, role)`；S0 校验：根为会话领头且 `sid != 监督器 sid`；阶段开始时监督器**没有**未登记子进程（枚举 `ppid == 自己` 必须恰等于已登记集合）；运行中出现的未登记子进程 → 立即 `UNKNOWN` + 可选 `INTRUDER` 诊断 | 新；NOT TESTED |
| O-3 | **专用监督器进程**（推断） | 监督器是一个极简、只做监督的新进程（`exec` 出的小程序），不加载可能偷偷 `fork` 的库；使「没有其它子进程」从人工声明变为**可由结构保证 + S0 检查验证**的性质 | 新；NOT TESTED；与 O-2 互补 |
| O-4 | cgroup 成员关系 | 每阶段放进专属 cgroup，成员关系即归属（含 `setsid()` 后代、孤儿）；cgroup v2 还有 `cgroup.kill` | 文档阅读。**本环境只有 cgroup v1 控制器（`/sys/fs/cgroup/cpu` 等），没有 v2 的 `cgroup.controllers`**；需要委派 / 权限；NOT TESTED，环境相关 |
| O-5 | 进程事件流（netlink proc connector） | 订阅内核的 fork / exit / setsid 事件，得到近乎完整的谱系，可发现「轮询间隔内诞生并孤立」的后代 | 文档阅读。本机内核配置有 `CONFIG_CONNECTOR`、`CONFIG_PROC_EVENTS`；通常需要特权（`CAP_NET_ADMIN`）；事件缓冲溢出（`ENOBUFS`）会丢事件 → 必须降级为 `UNKNOWN`；NOT TESTED |
| O-6 | 仅持有 pidfd 的跟踪 | 监督器在创建每个直接子进程时同时 `pidfd_open`，所有信号与等待经 pidfd；后代用「发现时立即 `pidfd_open` + 校验指纹」 | CPU-002 已验证 pidfd 信号语义；谱系发现仍需 O-2/O-4/O-5 之一 |
| O-7 | PID 命名空间隔离（`unshare`） | 阶段在独立 PID ns，内部全是阶段成员 | 文档阅读；需要特权、改变 `/proc` 视图与指纹语义；一般过重；NOT TESTED |

### 2.3 必须解决的开放问题

1. 「封闭世界」如何**强制**而非声明？O-2 的单一入口只能约束本进程内的代码；是否需要 O-3 把约束上升为结构保证？
2. 阶段**运行中**新增的辅助子进程怎么处理：禁止（出现即 `UNKNOWN`）还是允许但必须经登记？
3. 辅助进程的后代：登记时一并登记家族（`aux_family`），辅助进程死亡后其孤儿如何仍被识别？
4. 「轮询间隔内诞生并孤立」的真后代无法被轮询发现；是否接受 `UNKNOWN`，还是需要 O-4 / O-5？
5. `UNKNOWN` 的运营含义：D1 的名义工作负载里，期望 `UNKNOWN` 率是多少？由负责人定阈值（本文件只给出度量方式）。
6. `starttime` 分辨率为 10 ms（`CLK_TCK`=100）；同一时钟滴答内创建的进程如何排序？CPU-002 的做法偏向 `UNKNOWN`。
7. 指纹不能消除 TOCTOU（CPU-001 T-14c 已演示信号前替换会误杀）；pidfd 缓解单进程，整组信号的安全条件（提案 3.3）仍未测（T-15）。

## 3. 消费（E2）候选

目标：**每个子进程恰有一个消费责任方**；未知状态不得默认为成功；不确定则返回 `UNKNOWN` / `BLOCKED`。

### 3.1 已确认的事实（出处）

- 内核只有一份退出状态；消耗式读取后再读 → `ECHILD`（CPU-002 E2-01…03：之后 `waitid` → `ECHILD`）。
- 非消耗式观察：`waitid(P_PID, pid, WEXITED|WNOHANG|WNOWAIT)`，不影响后续 `Popen`（CPU-001 CB、CPU-002 E2-04 / E2-08）。
- **CPython 源码阅读（`/usr/lib/python3.11 / 3.12 / 3.13` 的 `subprocess.py`；NOT TESTED 于 3.11 / 3.12）：**
  - 三个版本的 `Popen._internal_poll` 都在 `waitpid` 得到 `ECHILD` 时设置 `returncode = 0`（带有「状态不可得」的注释）；本环境 3.13.16 的行为已由 CPU-002 实测。
  - **`Popen.__del__` 会调用 `_internal_poll(_deadstate=sys.maxsize)`**：对象被垃圾回收时若子进程尚未被等待，会对该 pid 做 `waitpid(WNOHANG)`——**可能静默消耗状态**。若子进程当时仍在运行，对象被放进模块级列表 `subprocess._active`，之后**每次创建新的 `Popen`**（`_cleanup()`）都会再次轮询它们。这是**另一条隐蔽的消费路径**，设计 B / C 必须处理。
  - `_waitpid_lock` 只保护**同一个 Popen 对象内**的线程竞争，不保护「Popen 与外部 `os.waitpid` 的竞争」。
- **SIGCHLD 处置继承（推断，Linux 通则，NOT TESTED）：**若启动监督器的父进程把 `SIGCHLD` 设为 `SIG_IGN`，该处置经 `exec` 继承，内核会自动回收子进程、状态永远不可得，Popen 将报告 0。S0 应校验 `SIGCHLD` 为默认处置。
- 本环境可用的 Python：3.11.15、3.12.3、3.13.16；**3.9 / 3.10 / 3.14 不可用，行为未验证**。`os.pidfd_open` 需 Python ≥ 3.9 且 Linux ≥ 5.3；`os.waitid(os.P_PIDFD, …)` 需 Python ≥ 3.9 且 Linux ≥ 5.4（文档阅读，NOT TESTED）。

### 3.2 三个设计（不预设优劣）

**设计 A — Popen 作为唯一回收者**

- 机制：直接子进程由 `Popen` 创建并**只**由 `Popen.poll()` / `wait()` 消费；监督器从 `p.returncode` 读状态（CPU-002 的 CA-P 是其局部原型：E2-01…03 的 15/15 PASS，E2-05 的 50/50 PASS）。
- 适用边界：对**直接 Popen 子进程**合理；**重新挂靠的后代与非 Popen 目标不是任何 Popen 对象**，仍需另一个回收者 → 实际上变成「Popen 管直接子进程 + 监督器管孤儿」两个回收者，**只有在 pid 集合严格不相交时才成立**；不相交性需要运行时断言（违反时 `ECHILD` → `UNKNOWN`）。
- 优点：不改变 Python 标准行为；`returncode` 已解码为 `-signal`。
- 缺点 / 风险：`ECHILD → 0`（只要有任何外部回收者，状态就被伪造成成功）；对象生命周期（`__del__` / `_active`）；线程语义仅限单对象；在 R3 中需要明确「谁创建 Popen、谁持有引用」。
- 未解决：如何对非 Popen 孤儿提供同等语义；`Popen.poll()` 的锁争用（返回 `None` 表示「未知」而非「运行」，见源码注释 "We know nothing yet"）是否被误读为 ALIVE。

**设计 B — 监督器作为唯一回收者**

- 机制：监督器直接 `os.waitpid(pid, …)` 消费并保存状态；**禁止**其他对象再消费。
- 要成立必须：不使用 `Popen` 对象的等待 / `poll` / `__del__`（可用 `os.posix_spawn` / `fork+exec` 创建，或确保 `Popen` 永不被回收且永不被轮询），并清除 `subprocess._active` 的影响。
- 优点：回收点单一、可审计；与 `waitid(WNOWAIT)` 的"先观察后消费"自然结合（CB 式）。
- 缺点 / 风险：与任何仍使用 `Popen` 的代码（含库）不兼容；状态同步责任全在监督器（崩溃时内存状态丢失，见 E3）；需要禁止 `waitpid(-1)`。
- 未解决：在已使用 `Popen` 的冻结 Driver / Reader 周围如何保证没有第二个消费者（源码审计范围）。

**设计 C — 统一 Reaper / 状态账本**

- 机制：一个拥有明确回收权限的组件（线程 / 子进程）独占所有 `wait*`；每次消费立即写**账本**（pid、starttime、状态、消费时刻、消费者标识），其他组件只读账本；账本可作为 E3 的恢复依据。
- 变体：C1 `waitid(WNOWAIT)` 观察 → 先写账本 → 再消费（**持久化先于消费**，崩溃不丢状态，代价是一个短暂的僵尸窗口）；C2 先消费再写账本（存在"内存已有、账本未写"的窗口）；C3 基于 pidfd 的事件驱动（`pidfd` 可读 → `waitid(P_PIDFD, …)`）。
- 与 Popen 的集成：用 Reaper 消费后把状态回填 `Popen.returncode`（依赖内部实现，NOT TESTED，需版本矩阵验证），或不使用 Popen。
- 优点：单一责任、可审计、可扩展到孤儿；天然与 E3 衔接。
- 缺点 / 风险：新增组件（复杂度、自身的崩溃面）；账本的持久化语义与冻结 R3 的事件 / 账本注册表（§2.4）及「不增加事件」约束（RA-10）如何共存——**可能需要 R3 变更**。
- **不能预先认定 C 优于 A 或 B。**

### 3.3 共同要求（所有设计）

- 未知状态不得默认为成功（`ECHILD`、锁争用的 `None`、`SIG_IGN` 自动回收、扫描失败均 → `UNKNOWN` / `BLOCKED`）。
- 状态读取幂等：重复读取返回同一份已保存结果，不触发再次消费。
- 不使用 `waitpid(-1)`、`P_ALL`。
- 回收前再次核对指纹。
- 退出码 / 信号终止必须符合独立真值，且区分 `exit(n)`、`-signal`、core dump 标志（`os.waitstatus_to_exitcode` 不保留 core 标志，设计需决定是否保存原始 `status`）。

## 4. 恢复（E3）候选

目标：监督器突然死亡时，**谁继续管理、谁终止遗留目标、谁回收僵尸、已取得的状态如何恢复、如何防止恢复程序误杀**。

### 4.1 两个必须区分的验收条件

1. **进程全部退出**（没有存活目标、没有无人负责的僵尸）。
2. **退出状态全部保存**（每个目标要么有来自独立真值一致的状态，要么被**明确声明**为 `STATUS_LOST`；绝不伪造）。

两者可以独立成立或不成立（例如 CA 在监督器崩溃后：条件 1 可由外层清理满足，条件 2 对已消费目标不满足）。

### 4.2 候选机制

| 编号 | 机制 | 内容 |
|---|---|---|
| R-0 | 冻结 R3 现状 | 监督器异常退出 → 预算结果 `UNPROVABLE`、运行状态 `ABORTED`、验收始终 `NOT_ACCEPTED`；`--postmortem` 只读取证据（11.9 F4）。**没有进程层恢复责任** |
| R-A | 外层 Watchdog / Subreaper | 独立进程在监督器之前启动并成为子收割者 / 持有监督器的 pidfd；监督器死亡（pidfd 可读）后接管：终止仍存活的已登记目标，回收僵尸并保存状态（CPU-002 E3-02a 的实验台就是一个原型） |
| R-B | 可恢复状态账本 | 关键身份（pid、starttime、角色）、已取得状态和回收进度持久化（追加写、`fsync` 策略待定）；恢复程序（可在监督器死后另行启动）读账本、验证指纹、再行动 |
| R-C | 组合 | Watchdog 管进程生命周期，账本保存关键结果；C1 式"先写账本再消费"使状态不丢 |
| R-D | 目标侧自我保护 | `PR_SET_PDEATHSIG`（父线程死亡时内核给子进程发信号；注意绑定的是**创建它的线程**，且存在设置时父已死的竞态，需要 `getppid()` 复核）；仅覆盖直接子进程，`setsid()` 后代不继承语义——只能作辅助，不能单独成立（文档阅读，NOT TESTED） |
| R-E | cgroup kill | cgroup v2 `cgroup.kill`（Linux ≥ 5.14）一次终止整个阶段；本环境仅有 v1 → 此项 NOT TESTED / 环境不满足 |

### 4.3 开放问题

1. 是否需要**自动**恢复，还是接受「监督器死亡 → `BLOCKED` + 手工 / 工具化清理」（R-0 加一个明确的清理工具）？这是范围与复杂度的权衡，需负责人决定。
2. Watchdog 自身失效怎么办（F07：监护组件无法接管）：谁监护监护者？是否接受"双故障 → `BLOCKED` 并留下诊断"。
3. 账本的写入时序、原子性、持久化级别（进程崩溃 vs 机器掉电）；本轮只考虑进程崩溃，掉电超出范围。
4. 恢复时的身份验证：pid 复用或指纹不符（F10）→ 必须停止并 `BLOCKED`，**不发信号**。
5. 恢复过程如何避免误杀非目标：只对账本登记且指纹匹配的 pid 行动；不使用 `pkill` / 按名称匹配 / `waitpid(-1)`。
6. 对改变了会话的后代（F09），恢复程序靠什么识别？依赖归属机制（O-2 的登记表 / O-4 / O-5）。
7. 与冻结 R3 的预算账本、事件注册表和 `postmortem.json` 的关系：进程层恢复的诊断落在哪里，才不违反"后验模式不向原账本追加"（R3 11.9 F4）？

## 5. 跨问题依赖与待决技术分歧

### 5.1 依赖表

| 若选择… | 则牵动… |
|---|---|
| 归属 O-2（启动登记表） | 恢复 R-B/R-C 可复用同一登记表（持久化）；消费设计 C 的账本可合并 |
| 消费 A（Popen 唯一） | 孤儿仍需另一回收者；恢复时 Popen 已消费的状态只在内存（崩溃即丢）→ 需要 C1 式预先 `waitid(WNOWAIT)` 记录 |
| 消费 B（监督器唯一） | 必须解决 `Popen.__del__ / _active`；崩溃保全依赖账本 |
| 消费 C（Reaper） | 与恢复 R-C 天然衔接；账本与 R3 注册表的关系需要 R3 变更评审 |
| 恢复 R-A（Watchdog） | 需要子收割者 / pidfd；Watchdog 失效需要降级规则；在无子收割者的环境（本环境 E3-02b）只能靠 pid 1 |

### 5.2 待决技术分歧（设计者识别；非审核者立场转述）

1. **封闭世界：声明 → 强制 → 消除。**O-2/O-3 把它变成可检验的结构；O-4/O-5 消除对它的依赖；O-1 以 `UNKNOWN` 容忍。
2. **严格变体的可用性。**O-1 避免误杀，但 `UNKNOWN` 率是否可接受？ChatGPT 的审核明确指出它"不能直接被选中"；阈值需负责人决定。
3. **Popen 是否应继续留在 R3 的监督路径里。**A 保留它；B/C 倾向绕开或包裹它。
4. **观察与消费的时序。**CB 式"先非消耗观察再消费"使"持久化先于消费"成为可能，但引入僵尸窗口与 T5 依赖（CPU-002 E3-01/03）。
5. **恢复是否自动。**Watchdog + 账本（复杂）vs `BLOCKED` + 清理工具（简单）。
6. **账本与冻结 R3 的关系。**新增持久化是否需要 R3 变更；RA-10"不增加事件"如何解释。
