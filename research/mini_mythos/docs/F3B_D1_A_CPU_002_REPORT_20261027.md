## 3. E1 — 目标进程归属安全

### 3.1 内核会话机制是否允许该拓扑（E1-S1，REAL_KERNEL，5/5）

- 正确启动（`start_new_session=True`）时，**阶段会话的成员恰好是根进程及其同会话后代**；`setsid()` 的后代自带新会话。
- 非阶段进程**无法**加入阶段的进程组 / 会话：一个尚未 `exec` 的同会话 fork 子进程调用 `setpgid(0, 阶段进程组号)` → `EPERM`（5/5）。
- **方法修订说明：**预注册的方法（对已 `exec` 的子进程调用 `setpgid`）得到的是 `EACCES`（5/5），因为内核先拒绝了「已 exec 的子进程」，根本没检查会话规则；这一错误方法的结果已记录并保留，判据内容（内核拒绝）用修订后的方法验证（REV-1）。
- **结论：**在正确启动的阶段里，「同会话非目标进程」**在内核层面不可构造**，因此 `sid_hint` 在正确启动下不会误归属；它只有在**阶段根不是会话领头**（与监督器共用会话）时才会出问题——这一错误配置的拓扑内核**允许**，见 E1-S2。

## 4. E2 — CA 与 `subprocess.Popen`

被测：真实 `subprocess.Popen(start_new_session=True)`；CA 的退出记录（`exit_status`）与 Popen 的内部状态（`returncode` / `poll()` / `wait()`）分别检查。对照 E2-00（仅 Popen）：退出码 7 / −9 / −15 各 5/5 正确，台架有效。

| 用例 | CA 自有记录 | Popen `poll()` / `wait()` | 判定 |
|---|---|---|---|
| E2-01 CA 先回收；退出码 7 | `exit 7`（5/5 正确） | **0 / 0**（应为 7） | CA **FAIL**（C2） |
| E2-02 目标被 SIGKILL | `signal 9`（5/5 正确） | **0 / 0**（应为 −9） | FAIL |
| E2-03 目标被 CA 自己的 SIGTERM 终止 | `signal 15`（5/5 正确） | **0 / 0**（应为 −15） | FAIL |
| E2-01…03 变体 CA-P（Popen 唯一回收者） | 全部正确 | 7 / −9 / −15 正确 | PASS（15/15） |
| E2-04 Popen 先 `wait()`，随后臂轮询 | CA：`UNKNOWN`（无记录，不声称状态）；CB：`UNKNOWN`；CA-P：`EXITED`，读到 7 | Popen 7 | PASS（15/15） |
| E2-05 竞态（50 次）：线程 `p.wait()` vs CA 轮询 | CA 赢 42 / Popen 赢 8 | CA 赢时 Popen 得 **0**（42 次）；Popen 赢时 CA 为 `UNKNOWN`（8 次） | CA **FAIL 42 / PASS 8**；CA-P 50/50 PASS |
| E2-06 CA 回收后 `terminate()/kill()/send_signal()` | — | `os.kill` 调用 **0 次**（INSTRUMENTED，只计数不执行） | PASS（5/5） |
| E2-08a CB 观察→**CB 的 T5**→`p.poll()` | CB 记录正确 | **0**（应为 7） | CB **FAIL**（5/5） |
| E2-08b CB 观察→`p.poll()` 回收→CB 再轮询 | — | 7 | CB 三态 `UNKNOWN`，PASS（5/5） |

- **根因（CPython 3.13.16 的 `subprocess`）：**当 `Popen` 的 `waitpid` 得到 `ECHILD`，它把 `returncode` 设为 **0**（「状态不可得」被伪装成「成功退出」）。CA 先回收后，Popen 对**任何**退出方式（码 7、SIGKILL、SIGTERM）都报告 0。这是**静默错误**，不是异常。
- **没有双重回收：**每次之后内核不再保存第二份状态（`waitid` → `ECHILD`，15/15 + 其余）；竞态里恰有一方取得真实状态（50/50），**没有**两方都丢失或两方矛盾的情况；无僵尸残留，Popen 对象自身无 `ResourceWarning`。
- **CA 的自有记录始终正确**（E2-01…03 共 15/15，E2-05 CA 赢的 42 次）；问题在 Popen 一侧的状态被破坏，以及**同一进程有两个状态持有者**。
- **CB 并非免疫：**CB 在 T5 之前不消耗状态（Popen 仍可读到真实状态，E2-04 的方向相反时 CB 得 `UNKNOWN`），但一旦 CB 自己执行 T5（E2-08a），Popen 同样报告 0。差别只是**窗口**：CB 在 T5 前对 Popen 无副作用。
- **缓解检查 CA-P**（让 Popen 成为唯一回收者，臂从 `p.poll()` / `returncode` 读取状态）全部通过——但这**改变了架构**：臂不再自己做「定向 `waitpid(pid)`」，对非 Popen 的子进程仍需另行处理。它是一个设计提示，不是已验证的最终方案。
- 版本依赖：以上是 CPython 3.13.16 的行为；其它 Python 版本**未测**。

## 5. E3 — CB 遗漏 T5

故障注入：跳过 T5（遗漏是被注入的故障；僵尸、`/proc`、回收行为是 REAL_KERNEL）。

- **E3-01（5 次）：**5 个阶段节点退出、CB 观察后不做 T5，4 s 窗口、每 0.5 s 采样：**CB 的僵尸在 225/225 个样本里持续为 `Z`，`kill(pid,0)`=成功 225/225（pid 持续被占用）**；CA 为 0/225（轮询时已回收）。**迟到的 T5 回收全部 5 个目标，状态与真值全部一致，残留 0**（恢复路径存在）。
- **E3-01b（台架，5 次，K=300）：**300 个子进程退出而不回收：300/300 为僵尸；`pid_max`=32768（占 0.9%），`RLIMIT_NPROC`=64279（root），仍能继续创建进程；`/proc/meminfo` 的 `Slab` 由 29752 kB → 32832 kB（+3 MB），`SUnreclaim` +2.6 MB（单次描述性数字，噪声大，不足以给出每个僵尸的成本）；逐 pid 回收后状态全部正确、残留 0。**结论：**滞留的是 pid 槽和内核的 task 结构，不是用户态内存；在本环境的规模下不构成资源耗尽，但是真实的、持续到被回收为止的占用。
- **E3-02a（监督器被 `SIGKILL`，无 T5，外层是子收割者；各 5 次）：**监督器死亡时所有阶段进程（含仍在运行的忽略 SIGTERM 的 D）都**继续存在**，被外层收养；外层仅凭 pidfd + 指纹逐 pid 清理：**CB：**未回收的 R、E、Y 僵尸的退出状态在外层**可读且等于真值**（3 / 5 / 9），D 被 pidfd 杀死并回收；**CA：**R、E 在监督器死亡前已被它自己回收，状态**不可恢复**（`pidfd_open` → `ESRCH`），只有未被回收的诱饵 Y 的状态（9）完好。两臂：残留 0；哨兵与诱饵未受影响；没有信号发给非目标。
- **E3-02b（外层不是子收割者）：**孤儿被 **pid 1（`process_api`）** 收养，监督器死亡后约 1.2–2.2 s 内僵尸被清理；D 仍在运行直到外层用 pidfd 杀死；两臂状态均**不可恢复**；残留 0。**该清理时间取决于本环境的 pid 1 实现，不应推广。**
- **E3-03（异常路径）：**观察后注入异常：CB 无 `finally` → 僵尸遗留 **5/5**（FAIL）；CB 加 `try/finally` 调 T5 → 全部回收、状态正确（5/5 PASS）；CA 无 `finally` → 已回收（5/5，状态在内存里，若异常传播则会随之丢失）。
- **共同风险：**监督器异常死亡**不会**终止仍存活的目标（无 `PDEATHSIG`、无进程组联动），这对 CA、CB 相同。

## 6. CA 与 CB：差异与安全风险（只对本轮结果）

| 维度 | CA | CB | 共同 |
|---|---|---|---|
| 与 `Popen` 混用 | 先回收→Popen 静默得 0（E2-01…05），竞态下 42/50 | T5 之前无副作用；T5 之后同样得 0（E2-08a）；Popen 先回收→CB `UNKNOWN` | 需要**唯一回收者**的约定 |
| 遗漏 T5 | 无影响（轮询时已回收） | 僵尸持续、pid 占用；需迟到 T5 / `finally` | |
| 监督器异常死亡 | 已回收目标的状态**丢失** | 未回收僵尸的状态可由新父进程读取 | 存活目标继续运行 |
| 归属安全（E1） | 与 CB 相同 | 与 CA 相同 | `closed_world_orphan` / `sid_hint` 在前提被违反时失败即不安全 |
| 退出状态来源 | 监督器内存 | 内核（直到 T5） | |

两者各有不同的失败模式，**没有任何一项把一方判为全面更优**；本轮也没有出现能支持「A/B 等价」的证据。
