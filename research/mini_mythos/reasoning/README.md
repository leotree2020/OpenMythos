# Stage R:推理探针(新的“尺子”)

规则见根目录 `CLAUDE.md`(宪章 v2.0)。负责人 2026-11-09 定的顺序:B(本阶段)→ C(循环编号)→ A(书籍遗忘原因)。本阶段**不训练任何东西**,只做一把新尺子,并用它量一遍原生 Parcae。

## 为什么要这把尺子

到目前为止,我们只测了“猜下一个词准不准”(NLL)。Mythos 假说说的好处是**多步推理**:循环多跑几轮,就能处理更多“步数”的问题。NLL 未必能反映这一点。

3b 的深度曲线显示,原生 Parcae 从 8 轮加到 32 轮,NLL 只好约 0.002。如果在推理题上多跑几轮明显更好,就说明之前用错了尺子;如果也没变化,说明这个规模上循环带来的推理增益本来就小。两种结果都有用。

## 探针(合成题,确定可复现)

每道题都给 3 个示范,再问第 4 题,答案从候选中选。不需要模型会“生成”,适合没做过对话训练的基础模型。

| 族 | 内容 | 难度级别(推理步数) | 候选 |
|---|---|---|---|
| chain | 变量传递,语句打乱,加干扰项:`x = 4. y = x. ...` 问最后一个变量 | 1、2、3、4、6 步 | 10 个数字 |
| order | 传递比较:`A is taller than B. ...` 问最高或最矮的人 | 2、3、4、5 个关系 | 链上的全部名字 |
| lookup | 键值查找,一步检索,作为对照 | 4、8、16 对 | 10 个数字 |
| add | 一位数连加,和不超过 9 | 2、3、4 项 | 10 个数字 |

- **数量**:开发集每格 200 题(共 3000 题);测试集每格 300 题(共 4500 题,本阶段不用,留给以后冻结的机制比较)。
- **答案核对**:每道题的答案都由一个**独立的解题器**从题面文字重新推出并核对;生成程序和解题器对不上就停止。
- **确定可复现**:题目由固定种子生成;sha256 记在 `results/sets_manifest.json`,GPU 机器上重新生成后必须一致。

## 打分

- 对每个候选,计算“提示 + 候选”中候选部分的对数概率总和;选概率最高的候选。
- 不加 BOS;提示和候选分别分词后拼接;FP32。
- 每道题的初始状态用固定种子在 CPU 上生成;同一道题的所有候选共用同一个初始状态,结果与怎么分批、怎么补齐无关(有测试保证)。
- 2 个副本,对数概率取平均。

**要超过的底线**(每格都报告):
- 名义随机猜:1/候选数;
- 总猜最常见的答案:例如 add 的答案偏大,这条底线会高于 1/10;
- chain 还有一条:从题面里随便抄一个数字。

## 本阶段要回答的问题(只报告,不设通过门槛)

1. **尺子能不能用**:原生 Parcae 在 8 轮时,哪些格子明显高于底线(Wilson 95% 区间的下界高于底线)?如果全部格子都在底线附近,这把尺子对 1.4 亿参数的模型太难,要换题。
2. **多跑几轮有没有用**:4、16、32 轮相对 8 轮,准确率差多少(按题配对,bootstrap 95% CI)?尤其是步数多的格子。

这把尺子的结果会写进 C(循环编号)的方案,作为 NLL 之外的第二个主指标候选。

## 文件

| 文件 | 作用 |
|---|---|
| `tasks.py` | 4 族题目的生成器和独立解题器 |
| `build_sets.py` | 生成开发集和测试集,核对答案,写 sha256 |
| `score.py` | 打分(单 token 候选快速路径,多 token 候选逐个打分);可通过 `--run` 给训练好的模型打分 |
| `report.py` | 每格、每个深度的准确率、底线、深度差 |
| `run_reasoning.sh` | 一条命令在 GPU 上跑完并推送结果 |
| `test_reasoning.py` | 5 个测试 |

**测试**(5 个,CPU,随机小模型,全部通过):
1. 生成确定;解题器与答案一致;
2. 解题器不是照抄生成器;
3. sha256 核对能发现不一致;
4. 分批打分与“一行一行”的独立计算一致(误差 < 1e-6);快速路径与逐个打分一致(浮点误差 2.4e-6);
5. 打分到报告端到端。

另外用随机小模型在本地把 `run_reasoning.sh` 走了一遍,推送到本地临时仓库。

## 预算

开发集 3000 题 × 4 个深度 × 2 个副本,计算量很小。估计 GPU 上 20–30 分钟,4090 不到 $0.5。

