## 2. 阶段 2 预算如何计时

**计入的时间**：一次 verify 或 freeze 启动，从进程启动（内核时间）算到账本区间关闭，包括：
- 解释器启动、全部导入；
- 子进程运行时间；
- 清理时间：终止进程组、写摘要和停止标记。

**不计入的时间**：
- 在 `env_checks` 阶段就因授权或环境被拒绝的调用：它们不读写任何文件，也不打开账本；
- 只读的 `check` 命令；
- 账本关闭之后到进程退出之间的几毫秒。

**执行顺序**：
1. 授权与环境检查；
2. 打开账本：先处理遗留区间，再判断是否超限，超限就立即拒绝；
3. 启动看门狗；
4. 安装绊线，导入代码，立即检查；
5. 执行各步骤：
   - 附录 A、键空间作业：受限等待；
   - 键规则核对：每 2000 个键检查一次；
   - V2：每 0.2 秒检查一次；
6. 在临时文件中写好最终文件；
7. 进入发布窗口：最后一次检查，然后 `link()`；
8. 写摘要；
9. 关闭账本区间。

**多次启动**：上限按全部区间的并集加补计累计，永不重置。

## 4. 无法保证零秒超限的部分（如实说明）

- **发布窗口**：
  - 最后一次检查之后只剩 `link()` 调用。正式运行中，从检查到两个文件都可见实测为 0.89 毫秒；开发运行中为 0.31–0.39 毫秒。
  - 如果上限恰好落在这段时间内，文件仍会按最后一次检查的决定发布，越过的量记入摘要，由审核决定。
  - 这段时间不能为零：`link()` 本身需要时间，操作系统也可能在任意时刻把进程调度出去。负载重时可能达到数毫秒，极端情况下更长。
- **看门狗的响应**：
  - 轮询周期 0.05 秒，加上 Python 处理信号的时机，实测超出 0.003–0.043 秒；作业轮询实测超出 0.024–0.047 秒。
  - 一次长时间的 C 层调用（例如 torch 导入中的扩展库初始化，或对单个大文件求哈希）会推迟处理函数，直到这次调用返回。
- **终止后的清理**：杀进程组时，SIGTERM 之后最多等 5 秒才发 SIGKILL。这段时间计入账本，表现为超出上限。
- **SIGKILL 只能事后处理**：驱动本身被 SIGKILL 或容器被回收时，账本留下一个未关闭的区间，由下一次启动按第 1 节的遗留区间规则处理。
- **作业自己的子孙进程**：`PR_SET_PDEATHSIG` 只作用于驱动的直接子进程。真实的作业（`e2c_stage4.py keyspace`、附录 A 脚本、V2 工作进程）都不再创建子进程；测试桩故意创建一个，`sigkill_driver` 记录到它在驱动被 SIGKILL 后仍然存活，随后由测试清理。正常停止时，进程组终止会把它一并杀掉。
- **未受限的调用**：本地 git 命令（毫秒级）没有包在受限等待里，但看门狗同样覆盖这段时间。
